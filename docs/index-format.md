## 2. FITS としての構造 [確認]

標準の FITS(2880 バイトのブロック、80 文字のカード)。どのファイルも HDU の並びは固定:

| HDU | TTYPE1 | 1 行のバイト数(NAXIS1) | 行数(NAXIS2) | 中身 |
|---|---|---|---|---|
| 0 | (primary, NAXIS=0) | – | – | 索引全体のヘッダー(§4)|
| 1 | `quads` | 4·DIMQUADS | NQUADS | quad の星番号 u32 |
| 2 | `kdtree_header_codes` | 0 | 0 | **データの無い表**。ヘッダーにコード木の KDT_* と CXDX 等 |
| 3 | `kdtree_lr_codes` | 4 | 葉の数 | u32 |
| 4 | `kdtree_split_codes` | 2 | 内部節点の数 | u16 |
| 5 | `kdtree_range_codes` | 8 | 2D+1 | f64 |
| 6 | `kdtree_data_codes` | 2·D | NQUADS | u16 × D |
| 7 | `kdtree_header_stars` | 0 | 0 | データの無い表。星の木の KDT_* と CUT*・SWEEPn |
| 8 | `kdtree_lr_stars` | 4 | 葉の数 | u32 |
| 9 | `kdtree_split_stars` | 4 | 内部節点の数 | u32 |
| 10 | `kdtree_range_stars` | 8 | 7 | f64 |
| 11 | `kdtree_data_stars` | 12 | NSTARS | u32 × 3 |
| 12 | `sweep` | 1 | NSTARS | u8(`TFORM1='1B'`)|
| 13 | `MAG_BT`(4 列表)| 16 | NSTARS | **4100 系だけ**。`MAG_BT, MAG_VT, MAG_HP, MAG` の `1E` |

- HDU の位置は表を見ずにヘッダーだけで決まる: ヘッダーは `END` カードを含むブロックまで、データは
  `NAXIS1 × NAXIS2 (+PCOUNT)` バイト(全表で PCOUNT=0)、データの後ろは 2880 の倍数まで詰め物。
  `kdtree_header_*` のようにデータが 0 バイトの HDU は、ヘッダーの直後に次のヘッダーが来る。
  [確認: 253 本すべてで「表のバイト数 = NAXIS1×NAXIS2」「ファイルサイズ = 詰め物込みの HDU の合計」]
- **HDU1〜11 の列の型は `'16A'` などの文字列型と宣言されているが、中身はバイナリ**(下のエンディアン)。
  astropy などで列として読むと文字列になって壊れる。**表は名前(TTYPE1)で探し、生のバイト列として読む**。
- 各表のデータは 2880 の倍数の位置から始まる(2880 = 64×45)ので、ファイル先頭からの位置は 64 バイト境界に揃っている。
  ページ境界から mmap すれば u16 / u32 / f64 のスライスとしてそのまま(コピーなしで)読める。
- 無い表: 木の外接箱(bb)、並べ替え表(perm)。`unpermute-quads` / `unpermute-stars` 済み(HDU0 の COMMENT)なので、
  **quad の番号 = コード木のデータの番号、星の番号 = 星の木のデータの番号**(§5・§8 で実証)。

## 3. エンディアン [確認]

- ヘッダーの `ENDIAN = '04:03:02:01'`(「u32 の 0x01020304 がメモリに 04 03 02 01 と並ぶ」= **リトルエンディアン**)。
  253 本すべての HDU0・木のヘッダーでこの値だけ。
- 実証(9 本で同じ結果): quads を `<u4` で読むと全要素 < NSTARS、`>u4` では成り立たない。lr は `<u4` で狭義単調増加、
  `>u4` では崩れる。range を `<f8` で読むと `[-1,-1,-1, 1,1,1, 2147483647.5]`、`>f8` では 1e-319 などの非正規化数。
- **例外: HDU13(MAG 表)は標準の FITS 表なのでビッグエンディアン**の float32。`>f4` で読むと 100% が -2〜20 等級に入り、
  `<f4` では約 63% しか入らない(4119〜4107 の 6 本)。
- 実装上は「`ENDIAN` が `04:03:02:01` ならリトル、`01:02:03:04` ならビッグ」と解釈し、MAG 表は常にビッグにする。

## 5. quads(HDU1)[確認]

- `NQUADS × DIMQUADS` の u32(リトル)。行 i が quad i、列は **A, B, C(, D)** の順の星番号(0 始まり、< NSTARS)。
- A, B が quad の「最も離れた 2 星」、C, D が残り(§8 で実証)。1 つの quad の星は全て異なる。同じ星の組の重複は 0。
- 星の使われ方: 4100 系の三角形で星の 66〜69%、4 星の系列で 90〜97% が少なくとも 1 つの quad に入る。
  1 星あたり平均 7.0〜9.7 個の quad(最大 8〜20)。

## 6. kd-tree(コード木・星の木で共通)[確認]

### 6.1 整数 ↔ 実数

- `kdtree_range_*` は f64 が 2D+1 個: **`minval[0..D)`, `maxval[0..D)`, `scale`**(ヘッダーの COMMENT にも同じ説明)。
- 実数 = `minval[d] + int / scale`。符号化は **`int = round((x − minval[d]) · scale)`(四捨五入)**:
  コードを星から計算し直して符号化すると、保存されている整数と **全 quad で完全一致**(切り捨てだと全成分が一致するのは 6〜25%)。
  [確認: 4119, 4118, 4115, 4111, 4110, 4107, 5206-00, 5206-01, 5202-00]
- 星: `minval = (−1,−1,−1)`, `maxval = (1,1,1)`, `scale = (2³²−1)/2 = 2147483647.5`。1 目盛り 4.66e-10(≒ 0.1 ミリ秒角)。
- コード: `minval = ½ − √2/2 = −0.20710678…`, `maxval = ½ + √2/2 = 1.20710678…`(全次元同じ), `scale = 65535/√2 = 46340.2429`。
  1 目盛り 2.16e-5。復号誤差は最大で半目盛り 1.079e-5(実測最大 1.0790e-5)。

### 6.2 木の形

- 節点数 `NNOD = 2^L − 1`(完全二分木)。番号は**ヒープ順: 根 = 0、節点 i の子は 2i+1(左)と 2i+2(右)**。
- 内部節点は 0 … `NNOD/2 − 1`(個数 = `kdtree_split` の行数 = (NNOD−1)/2)、
  葉は `ninterior` … NNOD−1(個数 = `kdtree_lr` の行数 = (NNOD+1)/2)。
- **葉 k(= 節点 ninterior+k)はデータ番号 `lr[k−1]+1 … lr[k]`(両端含む、`lr[−1] = −1`)を持つ**。
  lr は狭義単調増加、`lr[last] = N−1`。空の葉は無い(葉あたり 13〜26 点)。`KDT_LINL=F` なので lr は計算せず読む。
- 任意の節点の範囲: 左端の葉 = 2n+1 を葉に着くまでたどる、右端の葉 = 2n+2 をたどる。

### 6.3 分割(split)

- `kdtree_split` は内部節点ごとに 1 個(コード木 u16、星の木 u32)。
  **下位 b ビットが分割次元、残り(下位 b ビットを 0 にした値)が分割位置**(木の整数単位)。
  b = ⌈log₂ D⌉ → D=2 で 1 ビット、D=3・4 で 2 ビット。ヘッダーの COMMENT にも同じ記述がある。
  - `dim = raw & mask`, `val = raw & ~mask`(`mask = 2^b − 1`)。`raw >> b` と解釈すると左側の制約が 0% で成り立たない。
- 意味: **左の部分木の全点は `x[dim] ≤ val`、右の部分木の全点は `x[dim] ≥ val`**(両側とも等号あり。コードは量子化で同値が多く、
  左側にも val ちょうどの点が 1〜8% の節点で現れる)。さらに **`val = (右の部分木の dim 方向の最小値) & ~mask`** が 100% 成り立つ。
  分割次元はほぼ常に(99.8〜100%)その節点の点の広がりが最大の次元。
- 外接箱は保存されていない。根の箱は整数で `[0, 2^16−1]`(コード)/`[0, 2^32−1]`(星)と置き、分割位置で狭めていけばよい。

### 6.4 探索のしかた(そのまま使える)

- 箱検索 `lo ≤ x ≤ hi`: 節点 n で `lo[dim] ≤ val` なら左へ、`hi[dim] ≥ val` なら右へ(両方のこともある)。葉では点を直接比べる。
- 球検索(中心 c、半径 r): 節点ごとに箱を持ち、左の子は `hi[dim] = min(hi[dim], val)`、右の子は `lo[dim] = max(lo[dim], val)`。
  c と箱の最短距離が r を超えたら打ち切る。整数単位なら r に scale を掛ける。
- `anindex.kd_box_search` / `kd_ball_search` はこの規則だけで書いてあり、**9 本 × 2 木 × 40 問すべてで総当たりと結果が完全一致**。

## 7. 星(`kdtree_data_stars`)[確認]

- `NSTARS × 3` の u32。§6.1 で戻すと単位ベクトル `(x, y, z) = (cos δ cos α, cos δ sin α, sin δ)`(赤道座標、J2000/ICRS)。
  |xyz| − 1 の最大 3.95e-10・RMS 1.34e-10(四捨五入の量子化と整合。0.5 ずらす解釈だと 2 倍悪化)。
- **小さな角度を arccos で測る前に必ず正規化する**(または `atan2(|a×b|, a·b)`)。正規化しないと |xyz| のずれで数秒角の誤差が出る
  (Polaris: 正規化なし arccos 3.90″ / 正規化 0.38″)。`anindex.load_index` は既定で正規化する。
- 実在の星との照合(4110・4115・4119): Rigel 0.013″、Betelgeuse 0.26″、Polaris 0.38″ で一致。Altair 5.8″・Arcturus 20.0″ のずれ
  [推定: 固有運動の大きい星が古い元期(1991.25 前後)の位置のまま入っている]。
- **4100 系に Sirius・Vega・Canopus は入っていない**(4110 でも最寄りの星は 320″〜612″ 離れた 6.7〜9.8 等星)。最も明るいのは α Cen(MAG 0.137)、
  Arcturus 0.161、Capella 0.238、Rigel 0.283、Procyon 0.461。
- 並びは木の順(空間的にまとまっている)で、明るさ順ではない。

## 8. コード(`kdtree_data_codes`)[確認]

`NQUADS × D` の u16(D = 2·(DIMQUADS−2) = 4 または 2)。**行 i が quad i のコード**。列は `(cx, cy, dx, dy)`(三角形は `(cx, cy)`)。

### 8.1 定義(この式で全 quad の整数が完全一致する)

quad の星 A, B, C, D(単位ベクトル)について:

```
c   = (A + B) / |A + B|                      投影中心 = A と B の中点の方向(星全体の平均ではない)
η   = normalize(−c_y, c_x, 0)                赤経が増える向き(東)
ξ   = c × η                                  赤緯が増える向き(北)
各星 s:  x = (s·ξ)/(s·c),  y = (s·η)/(s·c)   心射(gnomonic)投影。x が北、y が東
z = x + i·y
w = (z − z_A) / (z_B − z_A) · (1 + i)        A → (0,0)、B → (1,1) に送る相似変換
code = (Re w_C, Im w_C, Re w_D, Im w_D)
```

- 平面内の回転は結果に効かない。効くのは**投影中心**と**向き(鏡像かどうか)**だけ。
  - 中心を 4 星の平均にすると、三角形の 4119 で最大誤差 0.0127、4107 でも 16% の quad が半目盛りを超える。中点なら全件が半目盛り以内。
  - 向きは (x, y) = (北, 東)。この座標系は x × y = −c(球の外向き法線と逆)。逆の向き(x と y を入れ替えたもの)ではほぼ全件が外れる(最大誤差 ≈ 1)。
- 極(c_x = c_y = 0)ちょうどの quad の扱いは未確認 [推定: どの向きを選んでも回転だけなので結果は同じ]。

### 8.2 正準形(対称性の破り方)

| 性質 | 内容 | 実測 |
|---|---|---|
| AB が最も離れた組 | 球面上の角距離でも、コード平面でも | 100%(9 本)|
| 4 星: `cx ≤ dx` | C と D の順 | 100%(1 目盛り以内)|
| 4 星: `cx + dx ≤ 1` | A と B の順 | 100% |
| 三角形: `cx ≤ 1/2` | A と B の順 | 100%(`cx + cy ≤ 1` は 71% しか成り立たないので別物)|
| CIRCLE: `(cx−½)² + (cy−½)² ≤ ½`(D も)| C, D は AB を直径とする円の中 | 100%(r² の最大 0.50002 = 量子化分)|

- A と B を入れ替えるとコードは `w → (1+i) − w`(各成分が 1 − 値)になる。C と D の入れ替えは列の入れ替え。
- **画像側の作り方**(`anindex.canonical_code(xy)`): 最も離れた 2 点を A, B に → 4 点なら `cx+dx > 1` で A↔B、続いて `cx > dx` で C↔D
  (3 点なら `cx > 1/2` で A↔B)。値の範囲は各成分 [−0.2071, 1.2071]、cx は [−0.207, 0.5]。

### 8.3 パリティ(鏡像)[確認: astropy の TAN WCS で 300 quad × 2 向き × 9 本]

- **FITS の画素座標(x 右・y 上)で det(CD) < 0 の画像(北が上なら東が左 = 普通の、鏡像でない空)では、画素座標からそのまま
  作ったコードが索引と一致する**(一致 100%、x と y を入れ替えると 0%)。
- det(CD) > 0(鏡像)の画像では、全点の x と y を入れ替えてから正準化すると一致(100%)。
- FITS の配列(行 0 が画像の下)なら (列, 行) をそのまま (x, y) に使えばこの規則どおり。
  **JPEG / PNG / TIFF のように行 0 が画面の上の画像では、(列, 行) をそのまま使うと向きが逆になる**
  (普通の空を表示どおりに写した画像なら、x と y を入れ替えるか y の符号を変える。[確認: 5206-00 の 200 quad で、
  上下を逆に格納した座標は直接 0%、y の符号反転 100%、x↔y 入れ替え 100%])。
  光学系(斜鏡・ダイアゴナル)でも反転するので、**ソルバーは両方の向きで引く**のが安全(astrometry.net の既定も両方試す [推定])。
- 符号化の一致は「WCS の接点を AB の中点に置いた」場合。接点がずれた場合は次項。

### 8.4 投影中心のずれによるコードの変化 [確認: `projcenter_check.py`、各 2 万 quad]

カメラ画像は光軸を中心とする投影なので、quad が視野の端にあると索引の「AB 中点で投影したコード」とずれる。
接点を AB 中点から |AB| の 0.5 / 1 / 2 倍ずらしたときのコードの距離(中央値 / 95% / 最大):

| 索引 | AB の中央値 | 0.5|AB| | 1.0|AB| | 2.0|AB| |

## 9. quad の大きさ [確認]

- **A と B の球面上の角距離 θ_AB が `SCALE_L ≤ θ_AB ≤ SCALE_U`** を全 quad(9 本)が満たす。最小/下限 = 1.0000001〜1.00048、最大/上限 ≤ 1.0000000。
- 弦の長さ |A−B| では 4119 で 0.7%、4118 で 0.55% が下限を割る → 基準は角距離。

## 10. sweep(HDU12)[確認]

- NSTARS 個の u8。値 0〜255。**「星を選んだ順(スイープ 1 の星を明るい順、続いてスイープ 2 …)での順位 r を 256 段に量子化したもの」**:
  値ごとの個数が `floor(256 · float32(r / N))`(r = 0 … N−1)の個数と全 9 本で完全一致(倍精度で計算すると 4107 と 5202-00 で数か所ずれる)。
- 裏づけ(4100 系 6 本): 同じスイープ内に収まる隣り合う値 v, v+1 で「v の最も暗い星 ≤ v+1 の最も明るい星」が全件成立(237/237・238/238)。
  スイープ番号ごとの MAG 中央値は単調増加(4107: 9.59, 10.49, 10.92 … 11.71)。
- `SWEEPn` の累積から、値 v の星のスイープ番号が分かる(`anindex.sweep_group`)。スイープ n は一様化セル(`CUTNSIDE` の HEALPix)ごとに
  n 番目に明るい星 [推定: HISTORY の `uniformize-catalog … sort column: mag … number of sweeps: 10` より]。
- 使い方: **値が小さいほど「早く選ばれた = そのあたりで明るい」星**。5200 系には等級が無いので、検証で「明るい星から n 個」取りたいときはこの値で並べる。
  MAG との順位相関(Spearman)は 0.68〜0.80(スイープをまたぐと明るさが戻るため 1 にはならない)。
- ファイル内の並び(木の順)とは無関係。

## 11. 等級(HDU13、4100 系だけ)[確認]

- 4 列とも float32 **ビッグエンディアン**(§3)。`MAG_BT`, `MAG_VT`, `MAG_HP`, `MAG`。**0.0 は欠測**。
- `MAG = VT(VT ≠ 0 のとき)、そうでなければ HP` が全件で成立。HP が入っているのは VT が欠けた星だけ(4107 で 2,200 個)。
- 範囲: 4107 で 0.137〜15.19(中央値 11.1、99% 点 12.7)、4110 で 9.46(中央値)、4115 で 6.27、4119 で 4.16。
- 5200 系にはこの表が無い(タグ列なし、HDU は 13 個)。

## 12. HEALPix(5200 系)[確認]

- ファイル番号 NN = HEALPix nside=2 の 48 ピクセルの番号だが、**番号付けは標準の NESTED / RING ではなく「xy」方式**:
  `NN = base·4 + x·2 + y`。ここで base は標準の基本ピクセル(0〜11)、NESTED の副番号 = x + 2y(x が偶数ビット、y が奇数ビット)。
  つまり nside=2 では NESTED の副番号 1 と 2 を入れ替えたもの。
  [確認: 5204・5205・5206 の 144 本と 5202-00 で、全星がピクセル NN に入るのは xy 方式。素の NESTED で合うのは 144 本中 72 本(副番号 0 と 3 のもの)]
- **星は自分のピクセルの中だけ**(のりしろ無し、`CUTMARG=0`)。quad はその星だけで作られるので、**ピクセル境界をまたぐ quad は無い**。

## 14. 落とし穴のまとめ

1. 表の列型(`'16A'` など)を信じない。生のバイト列をリトルエンディアンで読む。MAG 表だけはビッグエンディアン。
2. split の分割位置は `raw & ~mask`(シフトしない)。左右とも等号を含める。
3. コードの投影中心は「4 星の平均」ではなく「A と B の中点」。向きは x = 北・y = 東。
4. 三角形(4111〜4119)の正準化は `cx ≤ 1/2`。
5. quad の大きさは角距離(弦ではない)。
6. 星ベクトルは長さが 1 から最大 4e-10 ずれている。小角度の arccos の前に正規化。
7. 5200 系の HEALPix 番号は xy 方式。素の NESTED だと半分のファイルを取り違える。
8. 4100 系に Sirius・Vega・Canopus が無い。広角画像でこれらの星は対応相手がいない。
9. 4115 より広い索引では、画像側のコードを AB 中点で投影し直さないと許容差に入らないことがある(§8.4)。
